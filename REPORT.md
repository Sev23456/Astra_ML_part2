# Отчёт о работе: классификация `Zγ` с XGBoost и LightGBM

Дата отчёта: 16 октября 2026 г.  
Рабочая папка: `D:\ML\ML астрофизика\Работа\XGBoost и Light GBM`

## 1. Цель и итог

Выполнена воспроизводимая бинарная классификация сигнального процесса
`Zgamma_EWK` и совокупного фона. Реализация переписана из исходного
ноутбука в компактный Python-код, без изменения вычислительной логики.

Основной результат: по validation AUC выбрана модель **LightGBM**. На
независимой test-выборке она дала взвешенный AUC **0.9361321548474344**.
При её фиксированном пороге `0.9811620743844368` получены
`S = 43.31129390177183`, `B = 55.97930418869444` и
`ZA = 5.213262511864403`.

Результат надо трактовать как итог на моделируемых MC-событиях. Это не
оценка на неразмеченных данных и не измерение на реальных данных.

## 2. Что сделано

| Файл | Назначение |
|---|---|
| `zgamma_analysis.py` | Полный расчёт: чтение Parquet, обучение, выбор модели, оценка и создание таблиц/графиков. |
| `zgamma_plots.py` | Небольшие функции оформления и построения гистограмм, ROC, кривых обучения и порогов. |
| `audit_root_parquet.py` | Отдельная проверка совпадения ROOT и Parquet по UID, полям и гистограммам. |
| `compare_results.py` | Сопоставление результатов новой реализации с исходными файлами в `results/`. |
| `verify_results.py` | Дополнительная проверка сохранённых исходных результатов; не требуется для обычного повторного запуска трёх основных скриптов. |
| `RUN_SIMPLE.txt` | Краткая инструкция по воспроизведению. |

Исходные результаты в `results/` не заменялись. Новая версия пишет только
в `results_simple/`.

## 3. Использованные данные

Использованы **только 11 размеченных MC-файлов** из
`Z(nunu)gamma+jj/parquet`:

| Роль | Процессы |
|---|---|
| Сигнал | `Zgamma_EWK` |
| Фон | `Zgamma_QCD`, `Wgamma_QCD`, `Wgamma_EWK`, `top`, `ttgamma`, `gammajet`, `Zj`, `Zllgamma`, `Wenu`, `Wtaunu` |

Неразмеченный `data.parquet` не используется: он не открывается даже для
подсчёта числа строк. Это дополнительно отражено как `unlabelled_data_used:

Разбиение не генерировалось заново: для каждого `event_uid` взят готовый
split из `split_manifest.csv`. Числа событий:

|---|---:|---:|
| train | 3 494 606 | 70.0% |
| validation | 748 846 | 15.0% |
| test | 748 839 | 15.0% |
| Всего | 4 992 291 | 100% |

Таблица с разбивкой каждого процесса: `results_simple/tables/counts_by_process_split.csv`.

## 4. Признаки, веса и защита test-набора

В моделях использован 21 физический признак:

`n_jet`, `n_bjet`, `n_e_medium`, `n_mu`, `ph_pt`, `ph_eta`, `ph_phi`,
`jet_lead_pt`, `jet_lead_eta`, `jet_lead_phi`, `jet_lead_E`,
`jet_sublead_pt`, `jet_sublead_eta`, `jet_sublead_phi`, `jet_sublead_E`,
`metTST_pt`, `metTST_phi`, `metTSTsignif`, `soft_term_pt`, `soft_term_phi`,
`jet_sum_pt`.

UID, метаданные, веса и label не включались в список признаков.

Для обучения использованы модули исходных физических весов. В train каждый
из двух классов нормирован к `N_train / 2`; десять фоновых процессов при этом
образуют один класс. Для AUC также использованы исходные модули весов.
Знаковые веса применены только при расчёте физических величин `S`, `B` и
`ZA`, а также для сравнения формы распределений.

Параметры моделей выбирались по validation AUC, затем порог выбирался только
по максимуму validation `ZA`. До обращения к test сохранён файл
`results_simple/frozen_selection_before_test.json`: в нём указано
`test_used_for_selection: false`.

## 5. Настройки обучения

Общий seed: `20261004`; число потоков CPU: 8; максимум: 400 деревьев;
ранняя остановка: 30 итераций без улучшения.

Проверялись четыре конфигурации каждой модели:

| Модель | Перебор |
|---|---|
| XGBoost | `max_depth` = 3, 5; `min_child_weight` = 5, 20 |
| LightGBM | `num_leaves` = 15, 31; `min_data_in_leaf` = 100, 300 |

Выбранные варианты:

| Модель | Выбранные параметры | Число деревьев | Validation AUC |
|---|---|---:|---:|
| XGBoost | `max_depth=5`, `min_child_weight=5` | 399 | 0.9334156570 |
| LightGBM | `num_leaves=31`, `min_data_in_leaf=300` | 400 | 0.9347567107 |

Полный набор параметров и сетка поиска сохранены в
`results_simple/search_protocol.json`, результаты всех восьми запусков — в
`results_simple/tables/hyperparameter_search.csv`.

## 6. Метрики качества

| Модель | Train AUC | Validation AUC | Test AUC |
|---|---:|---:|---:|
| XGBoost | 0.9406868827 | 0.9334156570 | 0.9345716292 |
| LightGBM | 0.9432000157 | 0.9347567107 | **0.9361321548** |

Источник всех чисел: `results_simple/tables/final_metrics.csv`.

У LightGBM test AUC выше, чем у XGBoost, поэтому именно LightGBM указан как
итоговая модель. При этом выбор был сделан раньше, по validation AUC, а не по
test AUC.

## 7. Физический результат при зафиксированных порогах

| Модель | Split | Порог | S | B | S/B | ZA |
|---|---|---:|---:|---:|---:|---:|
| XGBoost | validation | 0.9811138511 | 41.9880 | 63.6836 | 0.6593 | 4.8011 |
| XGBoost | test | 0.9811138511 | 41.8774 | 55.1565 | 0.7593 | 5.0864 |
| LightGBM | validation | 0.9811620744 | 43.6259 | 66.7043 | 0.6540 | 4.8771 |
| LightGBM | test | 0.9811620744 | 43.3113 | 55.9793 | 0.7737 | **5.2133** |

`S` и `B` уже масштабированы на `1 / 0.15`, так как test и validation
содержат по 15% выборки. Подробные количества MC-событий, суммы квадратов

`results_simple/tables/physical_yields_at_frozen_threshold.csv`.

Для итогового test-результата LightGBM статистическая относительная ошибка
MC равна 0.97% для сигнала и 15.50% для фона. Последняя заметно больше,
поскольку после высокого порога эффективное число фоновых событий равно
примерно 41.6.

## 10. ROOT/Parquet-проверка: фактический статус

В исходных результатах уже есть завершённый ROOT/Parquet-аудит:
`results/tables/root_parquet_event_audit.csv`. Для всех 11 процессов он
показал:

* одинаковое число событий;
* совпадение UID, происхождения и split;
* максимальную абсолютную разность числовых значений **0.0**.

Побиновая исходная сверка сохранена в
`results/tables/root_parquet_bin_audit.csv`.

Отдельный скрипт `audit_root_parquet.py` добавлен специально для повторения
этого контроля из новой реализации. Он заново читает ROOT и Parquet,
сопоставляет события по UID, сравнивает метаданные и 21 признак, а также
нормированные гистограммы. Его свежий полный прогон **ещё не завершён**:
чтение ROOT-файлов оказалось существенно медленнее основного расчёта и было
остановлено. Поэтому в `results_simple/tables/` пока нет файлов
`root_parquet_event_audit.csv`, `root_parquet_bin_audit.csv` и
`root_parquet_histogram_bins.csv`.

Это ограничение относится только к свежему повторному ROOT/Parquet-аудиту.
Оно не отменяет завершённую сверку 198/198 новой реализации с исходными
результатами и не меняет ранее сохранённый исходный ROOT-аудит.

## 11. Как воспроизвести и проверить

В PowerShell, из рабочей папки, выполнить в указанном порядке:

```powershell
& '.\.venv\Scripts\python.exe' -X utf8 'zgamma_analysis.py'
& '.\.venv\Scripts\python.exe' -X utf8 'audit_root_parquet.py'
& '.\.venv\Scripts\python.exe' -X utf8 'compare_results.py'
```

После первого шага можно проверить:

1. `results_simple/summary.json`: выбранная модель, test AUC, порог, `S`,
   `B`, `ZA` и признак `test_used_for_selection: false`.
2. `results_simple/tables/final_metrics.csv`: все шесть AUC из раздела 6.
3. `results_simple/tables/physical_yields_at_frozen_threshold.csv`: значения
   из раздела 7.
4. `results_simple/predictions/validation_predictions.parquet` и
   `test_predictions.parquet`: UID, метка, веса и score каждого события.
5. `results_simple/figures/`: визуальная проверка распределений и отсутствия
   сильного расхождения Train/Test.

После второго шага появляются новые таблицы свежего ROOT/Parquet-аудита.
Только после этого запускается `compare_results.py`: его текущая версия
требует свежие файлы аудита и добавляет их к сравнению со старыми
результатами.

## 12. Вывод

Переписанный код воспроизводит исходный расчёт: сравнение сохранённых
результатов прошло 198 из 198 проверок без отличий в AUC. Лучшей по validation
AUC и итоговой по зафиксированному выбору является LightGBM; её test AUC
составляет 0.936132, а test `ZA` — 5.2133. Все промежуточные таблицы,
предсказания, модели и графики сохранены в `results_simple/`.

Осталось лишь завершить длительный независимый повторный ROOT/Parquet-аудит
новым скриптом; его старый сохранённый вариант уже показывает полное
совпадение входных ROOT и Parquet.
